# R8：评分草案整理与会话导入准备

本轮解决两件具体事：把已有规则整理成逐条工作清单，以及在会话进入评分前发现版本、编号和采集结构问题。代码与示例由助手完成，个人能力与独立复现仍待验收。

## 1．57条规则现在到了哪里

读取并核对已有私有 v0.4 草稿与公开审计的内容摘要，整理12例、57条规则。每条保留原有能力类别、触发和截止的文字草稿、0/1/2分标准、严重错误定义，并列出该病例可供核对的事实编号和披露事件编号。没有重新生成原病例或修改原审阅。

新的工作清单把下列事情分开：

| 内容 | 本轮状态 | 后续工作 |
| --- | --- | --- |
| 已有规则文字及分档标准 | 57条完整沿用，仍是未裁决草稿 | 逐条复核含义与歧义 |
| 触发事件及支持事实 | 列出可用编号，尚未选择 | 根据原文和披露方案选定；不按关键词自动关联 |
| 评价哪次回答、到哪里截止 | 保留原文字草稿；结构化提案为空 | 研究人员明确目标回答与截止策略，交评审核对 |
| 不适用／未到达条件 | 待明确 | 将无机会、未采到回答、未评分分别解释 |
| 实际触发／响应话轮 | 均为空 | 运行后依据真实会话记录；原始来源的话轮不等于未来会话的话轮 |
| 独立复核、实际映射、实际评分 | 均为0/57 | 各自验收，不能用“已整理”替代 |
| 临床裁决队列 | 12条 | 由合适临床人员处理；不是助手签字 |

私有清单为 `medical/patient-eval/local/readiness-r8/scoring-worklist-57-v0.1.json`，不提交患者文字到GitHub。公开数量见 `round-8-scoring-preparation-summary.json`。生成器只复制已有草稿，不生成医学建议；也不执行病例。

若持有原有私有材料，可在仓库根目录执行以下命令；`<私有草稿路径>` 由材料持有者替换，不提供患者文件的公开下载地址：

```bash
python -m scripts.patient_eval.scoring_worklist \
  --private-drafts '<私有草稿路径>' \
  --audit medical/patient-eval/data-sources/v0.2/dynamic-case-draft-audit-public-v0.1.json \
  --out medical/patient-eval/local/my-scoring-worklist.json
```

输出必须是忽略目录内的新文件。输入摘要或病例审计不匹配会拒绝；已有映射不会被重置。摘要用于检查是否拿错版本，不是独立的临床认证。

## 2．导入功能的具体变化

原来的 `patient_eval import` 仍保留。新增 `patient_eval.import_batch` 是严格版本绑定入口，输入为会话列表，输出仍为已有评分器可接受的会话列表。

它复用原来的角色、时间、证据及评分记录检查，新增：

- 同批会话编号唯一；同一病例重复试评需使用不同会话编号，汇总仍区分会话数与病例数。
- 每条会话声明的整套材料文件摘要、病例内容摘要必须与指定材料一致；同编号的病例修改后也不能继续沿用旧摘要。
- 病例、家族、变体、来源标签和会话方案必须匹配。
- 固定前缀方式要求角色与文字逐轮一致，成功时恰好一个最终回答；失败时没有该回答。自由对话方式校验首问，保留后续实际问答。
- 不接收空白回答、重复话轮编号、顺序错误、未知评分项及错误证据引用。目标接口失败与采集失效分别保留。
- 整批验证成功后才写入；已有结果不覆盖，竞争写入也不会替换旧文件。
- 不补评分，不做内部原因判断，不发网络请求。

采集时就应记录 `metadata.suite_sha256` 和 `metadata.scenario_sha256`；前者是完整材料文件字节的 SHA-256（Secure Hash Algorithm 256-bit，256位安全散列算法，用于版本比对），后者由 `scenario_digest` 对病例内容规范化后计算。工具不会在导入时替操作者追认未知版本。历史采集版本不明时，应回查原材料或单列为无法绑定，不用当前摘要假装已知旧版本。

## 3．无需模型密钥的可复现实例

环境：Python 3.10或更高版本，使用标准库，无新增依赖。命令从仓库根目录运行；受测代码版本以台账R8对应提交为准。每次更换新的输出文件名。

```bash
python -m scripts.patient_eval.import_batch \
  --input medical/patient-eval/readiness/bound-import-example-v0.1.json \
  --suite medical/patient-eval/development/scenarios.json \
  --out medical/patient-eval/local/my-import/sessions.json

python -m scripts.patient_eval evaluate \
  --sessions medical/patient-eval/local/my-import/sessions.json \
  --out medical/patient-eval/local/my-import/report

python -m unittest tests.patient_eval.test_import_batch tests.patient_eval.test_scoring_worklist -v
```

预期：1条公开合成会话、1个病例、没有人工评分。报告的4项规则均未评；会话完成率100%只说明这条模拟记录完整，不能当作医学正确率。再次导入同一输出应报拒绝覆盖，原文件保持不变。修改输入中的病例摘要，应在写入前报版本不匹配。

## 4．适用范围与下一步

这个入口处理既有 `patient-eval/v0.1` 开发会话格式，也可校验符合原有来源声明要求的已记录外部会话；导入成功不授予临床准入。未批准的12例动态 v0.4 草稿不能直接当成这套格式使用。不得更改来源标签来冒充合成病例；动态病例的准入后运行与格式适配仍待完成。

真实会话、本地导出和私有评分清单应保留在忽略目录；只有公开合成示例与不含患者文字的计数进入GitHub。摘要与操作者声明不能证明平台身份、采集真实性、脱敏充分或临床正确性。文件发布依赖同文件系统硬链接；不支持时明确报错，不改用可覆盖写入。

下一步优先由研究人员结合原文为少量规则提出明确事件关联和回答边界，再交独立评审；不要让医生重新编写整张清单。实际浏览器体验、他人复现与真实病例准入继续分别验收。
