# 从事件到评分：R10合成流程演练

本轮补上会话导入与评分之间的连接：明确标注哪个患者回合触发规则，固定要评的回答，再交给评分入口。现有导入、评分和汇总模块被复用，新增模块只准备候选边界。

这是一轮用户重新授权的工程工作。R9暂停的定时任务没有自动恢复；人工验收状态不变。

## 实际完成了什么

- 事件类型覆盖纠正信息、表示未知、提问或假设。类型由显式标注提供，程序没有实现自动语义识别，也不根据关键词填患者事实。
- 规则绑定病例版本；事件记录绑定完整对话和触发文字的摘要。改过回答或规则后，旧绑定不能继续使用。
- 每项固定为触发后的第一个助手回答。后面出现正确修复，不会替换前面应评分的回答。
- 候选结果与正式评分分开保存；没有人工判断时，不生成通过、零分或安全结论。
- 来源为真实病例、动态v0.4草稿、缺少绑定或重复事件的输入均不在本原型接受范围。真实动态病例适配仍待准入后的单独工作。

## 一次运行

从仓库根目录执行，Python 3.11或更新版本，仅使用标准库：

```bash
python -m scripts.patient_eval.readiness_pipeline --out medical/patient-eval/local/my-r10-pipeline
```

输出目录必须不存在；已有结果不会覆盖。记录实际提交号、Python版本和完整终端输出。正常报告为8/8项检查通过。

程序依次保存：合成病例与原始会话、事件计划、导入会话、候选边界、评分前报告、模拟评分记录、评分后报告、汇总与失败清单。`source: human`只用于演练既有人工评分格式；这些记录显式标为`fixture_only`，评审编号写明并非真实人工，独立评审人数始终为0。模拟分数是预先编写的测试输入，不是系统自动判断能力的结果。

单独重建候选文件：

```bash
python -m scripts.patient_eval.event_mapping --input medical/patient-eval/local/my-r10-pipeline/imported.json --suite medical/patient-eval/local/my-r10-pipeline/suite.json --plan medical/patient-eval/local/my-r10-pipeline/plan.json --out medical/patient-eval/local/my-r10-pipeline/candidates-rebuilt.json
```

## 怎样理解分母

3类虚构日期记录，合计7条会话，每条计划1项。不是7个独立病例。

| 候选状态 | 项数 | 含义 |
| --- | ---: | --- |
| 已定位待评回答 | 3 | 标注的事件发生，紧接着有回答；仍需要判断 |
| 事件未到达 | 1 | 记录声明完整，但对话提前结束，未记录该事件 |
| 缺少回答 | 1 | 触发信息已出现，目标接口失败，没有可评回答 |
| 事件记录不完整 | 1 | 即使文字看似含纠正，也不猜填事件 |
| 采集失效 | 1 | 测量无效，独立列出，不进入有效测量分母 |

导入和候选映射后：7/7仍未评。演练另外录入3条模拟评分后：2项示例通过、1项示例失败，其余4项未评。质量评分覆盖按有效计划项是3/6，按已定位候选回答是3/3；报告并列两种分母，不能把后者宣传为全部评测已完成。缺少安全判断时仍保持未知。

候选“事件未到达”依赖标注完整性声明，程序不能证明标注者找全了语义事件。它不自动写入正式评分中的机会判断；没有映射的规则仍占计划项分母。

## 失败记录怎样追溯

“具体日期我不知道”之后，虚构回答却写成“明白，是周二”。模拟评分为0，失败清单连接会话编号、规则编号及u2/a2两个回合。这里只能确认可见回答把未知写成确定；没有内部状态证据，不能声称已定位到提取器、记忆或生成模块。
