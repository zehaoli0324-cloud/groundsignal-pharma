# 一次完整的合成失败归因：纠正信息为什么没有生效

本轮完成 T06 的合成演练和可交接记录。主案例中，“服用时间”从“昨天”明确纠正为“今天早上”，但故障流程继续输出“昨天”。恢复纠正信息的传递后，状态和回答都使用“今天早上”。

这是已有运行器内人为注入的故障，本轮新增的是可重跑的调查入口、原始证据和反例检查。没有发现并修复一个新的线上缺陷，也没有测试真实模型。结果只能证明本地脚本的行为。

## 先分清四层

| 层次 | 本案例中的职责 | 这次看到了什么 |
| --- | --- | --- |
| 原文与提取 | 把原话转成结构化的事实更新 | 原文和更新都包含“今天早上”；更新由作者预先提供，没有测试自然语言提取器 |
| 传递与状态更新 | 把更新交给事实状态模块，并保留历史 | 故障分支跳过了更新调用；恢复后新值生效，旧值仍保留在历史中 |
| 回答生成 | 把当前状态写成可见回答 | 本地固定模板如实输出收到的状态；故障时输出旧值，恢复时输出新值 |
| 评分与诊断 | 判断行为是否符合预期，以及是否有足够证据归因 | 机械规则检查失败→通过；诊断还核对实际状态变化与输出，不能只相信声明的分数 |

“confirmed”在代码中表示明确记录的陈述，不能理解成已经获得临床确诊。“机械规则”指可精确核对字段的规则，本例没有自动判断医学语义。

## 从证据到修复的完整记录

| 环节 | 具体记录 |
| --- | --- |
| 原始证据 | 第一个用户话轮记“昨天”；最后一个用户话轮明确更正为“今天早上”。完整原文、更新、前后状态、回答和评分保存在报告的 `pairs[0]` |
| 预期行为 | 当前服用时间应为“今天早上”，来源指向纠正话轮；历史保留“昨天” |
| 实际行为 | 故障分支状态未变，回答仍是“昨天”；相应状态规则失败 |
| 候选解释一 | 提取没有识别纠正：本例预先提供的更新内容正确，可排除这份固定输入缺少纠正；不证明真实提取器可靠 |
| 候选解释二 | 更新没有传到状态模块：日志记录更新被丢弃，前后状态完全相同，支持继续检查这一层 |
| 候选解释三 | 状态正确但回答使用旧值：故障状态本身已旧，模板输出能由该状态重新构造，不符合这个解释 |
| 候选解释四 | 评分器误判：核对输出状态与期待值，并由现有诊断模块重新检查失败→通过；这是代码间的交叉核对，仍不是独立医学评分 |
| 固定条件 | 每一对运行使用相同原文、结构化更新、场景配置、检索结果和评分规则，执行编号不同 |
| 唯一干预 | `drop_correction=True` 改为 `False`，恢复同一条结构化更新的传递；不修改患者原话或期望答案 |
| 实际验证 | 故障时更新未送达，恢复后送达；新状态带有纠正话轮来源；输出能由真实状态重新构造；同一规则从失败变为通过 |
| 结论范围 | 在这次可观测的本地执行中，丢失纠正更新导致旧状态继续被输出。无法据此认定其他平台也存在同样内部故障 |

## 回归结果与分母

| 用例 | 故障状态 | 恢复后状态 | 同一状态规则 |
| --- | --- | --- | --- |
| 主例：服用时间 | 昨天 | 今天早上 | 失败→通过 |
| 已有回归例：有无头晕 | 没有 | 有 | 失败→通过 |
| 已有回归例：报告日期 | 2024-01-10 | 2025-01-10 | 失败→通过 |

总计3个公开合成开发用例、6条本地脚本会话。后两例是既有公开模板的回归，不是独立保留测试，也不是新发现的模型失败。每例另有2条临床/理解类规则，6条会话共12项均保持未评；不能把机械检查通过写成临床安全通过。

演练的15项检查来自：3例各检查“状态失败→通过、匹配干预支持归因、临床规则保持未评”，共9项；再加6项归因边界检查。它是工程检查分母，不是患者、评审人数或模型正确率。

## 哪些情况不允许确认内部原因

| 反例 | 验证结果与意义 |
| --- | --- |
| 没有恢复动作，重新提交旧失败 | 拒绝；不能用一次重跑声明修好了 |
| 只把回答和分数改成正确，状态仍旧 | 拒绝；输出和分数声明不能替代真实状态变化 |
| 缺少状态变化记录 | 拒绝；无法确认更新实际送达并生效 |
| 对照时改变执行配置 | 拒绝；多个变化混在一起不能归于单一干预 |
| 只有黑盒对话，看不到内部记录 | 拒绝确认内部原因；最多报告可见症状和候选解释 |
| 只有失败，没有配对恢复 | 保持待调查；看到错误不等于已经知道原因 |
