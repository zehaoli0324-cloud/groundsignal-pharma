# 人工平台采集协议 v0.2

本协议先用 12 个公开合成变体验证采集方法，再接入经许可、去标识的真实问题。目标是比较实际可见的问询和解释行为。当前材料未经过临床审核，不能据此宣布某个平台适合真实患者独立使用。

## 1. 采集之前冻结什么

固定 `suite.json` 文件及其 SHA-256（Secure Hash Algorithm 256-bit，256 位安全散列算法，用于识别文件是否改变）摘要、协议版本、评分版本、平台条件、每轮等待预算和重复次数。记录实验开始前的提交版本。任何中途改题、改披露或改评分，都开启新版本，并保留原试评记录。

本轮两个平台是“小荷健康应用”和“一个明确名称及模式的通用模型”。实际名称、应用版本、账号设置和采集时间由操作者填写，不能由示例替代。每个场景都使用新会话；跨会话记忆能关闭则关闭，不能关闭或状态不明则如实记录为未知。不要把“开了新会话”等同于“系统不可能保留记忆”。

每一轮实验必须固定以下条件：

| 条件 | 记录要求 |
|---|---|
| 产品状态 | 应用／网页版本；不可见版本写“界面未提供”，不要猜底层模型版本 |
| 能力模式 | 文本输入；是否联网、深度思考、记忆或个性化；不可控制的项写未知 |
| 时间和设备 | 有时区的开始／结束时间、设备与系统、网络类型和采集窗口 |
| 账号与会话 | 本地匿名账号代号、新会话是否确认；不保存登录密钥和账号个人资料 |
| 运行预算 | 每轮最多等待 120 秒，助手最多回答 10 轮；这是预设试评预算，不是医疗服务标准 |
| 重试 | 主试评不点击重新生成、不挑最好结果；超时按原运行记录，另开诊断重复 |
| 版本变化 | 同批采集中发现模式或版本变化则分批报告；不混为同一条件 |

在同一家族、同一重复轮次内，两个平台尽可能在接近的时间运行。预先随机确定平台顺序及 clear／pressure 顺序，并保存随机种子和实际顺序；不要总是先做小荷或总是先做清晰版本。若无法随机化，明确记录固定顺序这一限制。

本轮 24 条会话只用于试跑协议。协议稳定后的 72 条会话仍是 6 个开发家族，不能宣称有 72 个独立场景或给出全面临床排名。

## 2. 动态会话如何操作

1. 复制该变体的 `initial_user_message`，不要发送整份场景、隐藏事实、事件表或评分标准。
2. 完整保存平台实际回答，按 `u1`、`a1`、`u2`、`a2` 顺序编号。不要替换不理想回答，不要删掉重复或冗长内容。
3. 模型问到了哪个事实，就按固定 `facts[slot].answer` 回答。能一次合理回答多个已问事实时，可合并这些回答并记录所披露的槽。没有问到的关键事实不主动赠送。
4. 处理否定问句、含糊指代和同义问法时，以实际问题语义为准。普通关键词只用于自动原型调度；若人工判断问得合理但自动规则漏匹配，记录为模拟器规则缺口，并按已冻结的事实回复。
5. 更正事件仅在先前对应事实已经披露、且达到最低助手轮次后触发；明确说出更正，不抹去旧消息。更正代表报告者修正记忆，不是模型可以预先读取的事实。
6. 达到事件条件后，在下一个用户回合优先释放事件，再在后续回合处理新的事实追问；同一事件只发送一次。本版严格按事件表顺序，更正之后才是预声明压力和错误复述；不得越过前一个尚未触发的事件。记录真正发生的事件和触发依据，不能假定所有事件一定发生。事件可能暂时打断模型当轮追问，这属于已固定的交互条件，两个平台一视同仁。
7. 压力文本严格按变体发送。不要临时增加更严重症状、编造剂量、替患者提供不知道的报告数值，或根据某个平台表现“救题”。事实表没有覆盖的追问，回复“这点我现在不清楚”，并记录未覆盖的问题。
8. 如达到最大助手回合，保留真实最后回答及尚未到达的任务；不要额外加一次免费的总结回合。若交互器安排了收尾提示，它也必须占用既定用户／助手预算。

模型主动说明需要现实中的专业帮助或合理结束时，操作者可以结束采集，记录具体可见依据，再由评审者判断哪些后续判据正当不适用。不能一看到“咨询医生”就自动判为任务成功，也不能为了发完所有事件而忽略正当停止。

模拟器审计应分开保存“问了什么、披露了什么、事件是否触发”和“模型回答是否合格”。披露次数、轮次长度和问题数量都不是问询能力的替代分数。

## 3. 同一病例，不强求相同对话路径

本套件采用 `comparison_lane=free_dialogue`（自由多轮交互：下一条用户消息取决于模型的实际问题）。两个平台使用同一冻结事实和披露规则，可以问不同的问题、走不同路径。这衡量完整会话的表现，但单个回合差异不能直接归因于某一内部模块。

另做局部对照时，才使用 `comparison_lane=fixed_prefix`（固定前缀：每次运行接收到完全相同的合法历史消息），并另建协议。应用通常不能注入过去的助手角色；把一段历史粘进用户输入，只是“用户提供的引用文本”，不等同于真实历史前缀。不要声称通过应用完成了它不支持的角色注入，也不要把这种文本探针和自由会话汇总成一个指标。

如果前一轮回答不同，不能为了凑成配对而伪造相同助手历史。完整会话按家族、变体、平台、重复轮次配对；局部原因探针需要独立记录其可控制范围。

## 4. 记录什么，如何处理失败

[collection-template.json](collection-template.json) 是空表规范，不是已有小荷结果。每条完整记录包含可见对话、运行状态、匿名操作者、版本时间和协议信息；内部 `trace` 始终为空，不能把推测的检索日志填进去。

| 情况 | 会话状态 | 分析方式 |
|---|---|---|
| 正常回答并到达结束条件 | `completed` | 按实际出现的机会逐项评分；未标注项保留未评 |
| 平台超时、报错、输出为空或客户端会话丢失 | `target_error` | 保留运行分母，记录未完成任务；不是自动证明医学严重错误 |
| 操作者漏贴消息、记录丢失或模拟器发错事实，已无法复原 | `measurement_invalid` | 需给出独立测量原因；单列数量和证据，不进入有效测量分母 |
| 平台回答差、拒答或走了不理想路径 | 不得仅凭此标为 `measurement_invalid` | 这是待评的目标行为，不能从分母中剔除 |

完整回答保存原文；截图只在合法且必要时本地保存，并记录本地引用。若流式输出中途停止，记录已显示的部分、开始时间和截止时间，不能补写“它大概想说什么”。另行复跑必须有新的 `session_id`，与原记录建立关联，并标记为诊断或新重复；原失败保留。

采集助手给出的下一句患者文本在实际提交前只是草稿。无回答故障必须明确记录提交状态：`--target-error --patient-submitted` 才会把最后用户输入作为已提交内容导出；`--target-error --input-not-submitted` 只追加采集问题，保持未完成日志，不虚构平台已经看到开场、纠正或风险信息。收到并录入平台对这条输入的真实回答后，才将该轮确认为已发生的交互。

## 5. 接入真实问题

真实问题进入下一阶段前，要确认有权用于该评测，并去除姓名、联系方式、精确身份、可识别截图等信息；保留会影响任务含义的相对时间、年龄分层或用药事实时，应检查重新识别风险及医学含义是否改变。去标识和使用许可是操作者的声明，不是程序完成了法律或临床审核。

真实问题不得直接覆盖合成套件的 `source=synthetic`。另建 `source=deidentified_real` 的本地材料及来源记录，并标记临床审核状态。对照版本只能改变预声明表达或压力因素；改变病情、关键事实或任务目标就需要新家族，不能仍然当作同一个轻微改写。

采集用于评价系统，不用于给问题当事人提供即时诊疗。公开仓库仅保存合成场景、代码、协议和经审阅的汇总；真实原文、截图、身份映射及账号信息留在受控本地位置。上传任何实例前单独检查权限与去标识情况。

## 6. 本轮结果如何表达

先报告有效会话数、平台服务失败、测量失效、评分完成率及分歧，再报告各能力判据。缺陷卡片引用具体回合，记录“观察到的行为—改变哪个条件—对照是否恢复—仍存在什么候选解释”。

对小荷或其他只能看到输入和输出的平台，只能写“该行为支持某种缺陷假设”；不能仅凭一次忘记更正就确认内部存在状态数据库错误、上下文截断或某种模型算法缺陷。对自建系统，额外使用真实输入记录、组件日志和修复回放，才能提高原因判断的证据等级。
