## 1. 为什么并入现有项目

新需求与 GroundSignal 已有的案例、证据段落、错误标签、干预假设和回归机制直接相连。新建完全独立仓库会重复建设这些基础设施，也容易使证据版本和缺陷编号脱节。建议用模块边界隔离患者会话执行与评分，用共享标识关联已有证据和案例。

需要扩展的是评测对象：从一次回答和预置证据，扩展为随交互变化的患者会话。页面可以保留一个“患者评测”入口，在内部提供八个能力模块、三种运行模式，不必创建八套应用。

| 组织维度 | 用途 | 不应混淆的内容 |
| --- | --- | --- |
| 一个入口 | 选择场景、平台、运行条件和报告 | 一个入口不等于一个总分 |
| 八个模块 | 语义澄清、主动问询、事实更新、风险边界、证据适用、工具恢复、患者解释、压力稳定 | 模块是能力；症状、用药、报告、随访等是业务场景 |
| 三种模式 | 模块专项、完整会话、诊断回放 | 完整会话成绩与局部回放结论分别报告 |
| 两种观测等级 | 可记录内部过程的系统、只能观察用户界面的平台 | 不能按同一种证据标准宣称内部根因已定位 |

以后如果团队、权限、部署节奏或数据管理已明显独立，再将执行服务或受控数据服务拆出。现在先形成清晰接口和独立测试；拆仓库不是能力成熟的前提。

## 2. 当前项目处于什么阶段

基线代码已具备医疗评测研究底座和可执行的局部工具。它还不是可直接面向患者提供咨询的医疗智能体，也不能仅凭代码结构判断其达到某个商业医疗模型水平。商业平台的内部训练、检索、路由和质量控制情况在本项目中没有可验证依据。

| 已核对的仓库位置 | 当前可用能力 | 患者多轮系统的差距与适配方式 |
| --- | --- | --- |
| [`scripts/model_harness.py`](../../scripts/model_harness.py) | 固定响应夹具；通过兼容接口调用模型；记录提示、回答、延迟和用量 | 一次运行仍将历史组装进单次请求；证据按允许段落列表取前若干项，不能视为按问题检索；工具轨迹目前为空。首版新执行器记录固定前缀及可见标注产生的状态轨迹，生成最后回答；动态逐轮提问和工具调度属于下一阶段 |
| [`scripts/s2_live_retrieval.py`](../../scripts/s2_live_retrieval.py) | 接入 DailyMed、美国食品药品管理局、ClinicalTrials.gov、RxNorm、PubMed 等来源；区分网络、响应和解析失败 | 来源连通不等于患者问题相关性。先冻结段落快照，再测检索排序与适用性；下一阶段通过适配器接入在线来源 |
| [`scripts/s2_dailymed_truth_retrieval.py`](../../scripts/s2_dailymed_truth_retrieval.py) | 版本检查、说明书段落提取、关键词和标题加权排序 | 补充明确的检索基线、错人群/旧版本干扰项和查询变化实验；不把规则排序描述为神经重排序 |
| [`scripts/s3_semantic_extractor.py`](../../scripts/s3_semantic_extractor.py) | 确定性规则基线与可选模型结构化抽取；对字段和枚举做检查 | 对患者口语还需要人物、否定、时间、未知和纠正标注。先用可见结构化事件测试状态更新，再独立评估自然语言抽取；两者不能合并宣称语义能力已达标 |
| [`medical/knowledge-graph/HOW_IT_IS_BUILT.md`](../knowledge-graph/HOW_IT_IS_BUILT.md) | 案例局部医学图、药理安全骨架和合并层；保留来源段落与适用关系 | 可复用事实和证据标识；不能假定已经覆盖完整医学知识或所有患者问题 |
| [`scripts/intervention_router.py`](../../scripts/intervention_router.py) | 将错误标签映射成干预候选，并保留“尚未因果证明”状态 | 新诊断器补充可观察证据和受控对照；故障分类本身不构成根因验证 |
| [`scripts/regression_gate.py`](../../scripts/regression_gate.py) | 同案例的指标、严重错误与回归对照 | 新增会话、事件、家族和条件标识，随后通过映射接入；本次不改旧门禁 |

本次采用增量路径：先让患者评测在合成开发轨独立跑通，再连接原有证据和缺陷流水线。现有 S5、S6 阶段准入、独立测试污染控制、专家审核及训练导出规则继续有效；本子系统的开发成功不能替代正式放行。

## 3. 两项能力必须分别证明

**我们自己的算法与工程能力**：能够提出可检验的算法改动，保留正确对照，量化何时改善、何时退化；能够让每条会话可追踪、失败可重现、结果有明确分母、数据和评分版本可追溯。

**发现被测平台不足的能力**：能够用可观察的会话证据确认行为缺陷，再按证据强度提出原因和下一步实验。报告需要告诉读者“看到什么”“哪些原因仍然可能”“什么新证据能区分它们”。

| 观测等级 | 可记录材料 | 可以成立的结论 | 不能直接成立的结论 |
| --- | --- | --- | --- |
| `instrumented`：有内部过程记录 | 实际发给模型的输入、状态变更、检索排序、工具请求与响应、组件版本、时间线 | 在匹配对照与故障证据齐备时，验证特定条件下的状态更新、接口映射、检索或生成策略问题 | 一次修复有效就证明其他所有案例同一根因；组件失败就证明真实患者受害 |
| `black_box`：只能观察结果 | 患者输入、完整回答、界面可见引用和错误、版本与采集条件、端到端等待时间 | 纠正未被吸收、回答前后冲突、解释未修复误解等行为缺陷；受控比较支持的候选解释 | 直接确认使用何种模型、上下文被后台截断、检索器失灵、某算法未部署、服务器具体故障 |

证据等级采用“在本实验条件下已验证”“有对照支持的假设”“待排查”。黑盒报告的内部算法或工程原因保持假设，即使行为重复出现也不能升级成内部实现事实。能验证的是输入条件与输出行为之间的关系。

例：用户在第六轮纠正日期，下一轮回答继续使用旧日期。只有回答时，可以确认纠正吸收失败；可能是信息使用不足，也可能是会话状态、输入处理或上下文传递问题。如果在新的固定前缀中明确重述新日期后恢复，可支持“与历史信息使用有关”的解释，仍不能据此断言后台截断。如果自己系统的日志证明纠正未进入实际模型输入，修正状态合并器后相同前缀稳定恢复，才有条件确认该组件的工程故障。

界面超时也应记录，但它首先是用户可见的服务失败；除非进一步区分设备、网络、客户端和服务端，不把端到端等待时间直接称为服务器推理延迟。

## 4. 小荷与通用模型的研究设计

### 4.1 先形成可以复核的采集协议

第一轮使用文本输入，手动在小荷应用和选定通用模型界面提交问题，人工导入完整会话。应用程序接口（Application Programming Interface，API）模式作为另一接入渠道记录，不能默认与应用界面提供了相同系统提示、联网、记忆、路由或工具能力。

患者问题必须有明确来源：本人提供且同意用于研究的问题、取得相应使用许可并去标识的材料，或符合使用条件的公开问题。保存来源类型与使用依据；研究集中的“真实问题改写”与原始真实问诊日志分别计数。去标识化需人工复核，不能依赖一个正则表达式声称已安全。

公开仓库只提交合成样本、空白模板、代码和经复核的不可识别汇总。真实问题、报告图片、录屏、会话原文、账号信息及可关联身份的映射保存在受控位置，导入结果默认作为本地研究数据。不得将评测过程中的回答用于指导原患者医疗决策。

每次采集至少登记以下条件。字段未知就写“未知”，不编造模型版本。

| 对象 | 必填记录 |
| --- | --- |
| 平台 | 界面显示名称、应用版本或网页版本线索、模型显示名称、采集日期与时区、界面或 API 渠道 |
| 环境 | 设备与网络条件、账号类型、可见的记忆/联网/检索开关、图片或文件能力、所选模式；账号标识用不可识别的研究编号 |
| 会话 | 家族与变体标识、实验条件、重复编号、启动新会话情况、每轮顺序、原文、时间、可见引用、完整结束原因 |
| 异常 | 空回答、服务报错、重试、人工改输入、粘贴失败、截断、上传失败；保留失败会话，禁止仅保留成功重跑 |
| 数据与审核 | 来源和使用依据、去标识复核、临床评分者、评分规则版本、分歧与裁决；导入者与评分者尽可能分离 |

会话开始前按协议重置可控记忆并新建会话；无法确认跨会话记忆时，记录限制并分组报告。先以少量合成问题检验导入模板，再接入经审核的真实问题改写。采集者不能临时增加仅有某个平台才获得的关键患者信息。

### 4.2 自由对话与固定前缀分别实验

**自由对话轨**检验完整任务能力：同一患者事实、初始问题、可披露条件、轮次与时间预算，由平台自主提问。采集者按冻结规则回答；平台未问到的信息不会为了完成剧本而自动送出。不同平台可能走不同分支，比较的是同一家族下的整体任务结果，而非要求每轮文字完全相同。

**固定前缀轨**检验局部响应：使用相同且合法的已披露会话前缀，在指定节点加入纠正、歧义或误解探针，比较后续回答。必须明确平台实际接收了完整历史还是用户粘贴的引用文本；仅能粘贴文本的应用不能被描述为接收了同样的结构化会话消息。

两轨单独标记和汇总。固定前缀有助于缩小差异来源，但不能代替自由对话的主动问询评测。将所有关键事实直接放进初始问题得到的成绩，也不能代表模型会主动追问。

### 4.3 形成公平、可解释的对照

1. 按家族配对清晰版和压力版；核心患者事实及评价目标保持一致，仅预先指定的压力因素不同。
2. 记录哪些条件能够控制，哪些是平台固有配置。小荷应用对通用聊天应用属于端到端产品比较；自建 API 组合属于模型与系统组合比较。报告不可把它们简写成底层模型能力排名。
3. 在尽量接近的时间窗口交错采集；随机或平衡平台及变体顺序；每次新建会话，同版本同模式进行预先规定的重复。平台更新后单独记录批次，不能混作原版本重复。
4. 评分隐藏平台名称与先后位置；保留内容本身的引用、结构和必要的上下文。临床规则由合适的临床人员审核，出现分歧时留痕裁决。
5. 记录纳入和排除流程。目标平台超时、未完成或错误停止算目标失败；独立采集故障或评测器错误才可标记测量无效，并报告数量与原因。
6. 冻结问题、规则和比较条件后再开展正式测试；不能看完哪个平台答得好再调整标准或补充提示。

### 4.4 黑盒中可实施的缺陷探针

| 探针及匹配对照 | 可以观察到的缺陷 | 可以提出的假设 | 下一步区分实验 |
| --- | --- | --- | --- |
| 清晰指代与口语省略，其他事实相同 | 错认咨询对象；凭空补全药名 | 歧义消解或澄清策略不稳 | 增加明确对象标记；分离指代、否定、药名未知因素 |
| 同一纠正放在短历史和较长干扰历史中 | 旧事实残留；错误随位置或干扰变化 | 对历史信息、纠正或上下文位置敏感 | 固定前缀重述新事实；改变纠正位置，保持总信息量可比 |
| 相同任务有无经过审核的证据摘录 | 给定证据后回答才改善，或仍不使用 | 外部知识获得、证据使用或生成策略可能薄弱 | 控制摘录长度与格式；加入相关但不适用的对照，避免只测额外提示强度 |
| 中性请求与催促保证 | 无依据保证、建议边界改变 | 对用户压力的策略稳定性不足 | 区分催促、焦虑、权威暗示；重复并检验内容差异 |
| 正常复述与固定错误复述 | 未纠正过度推广或错误理解 | 面向患者的解释和理解检查不足 | 用新的等价误解复测；由人判断修复是否准确可懂 |
| 同会话、同条件的重复与不同时间批次 | 行为波动、服务错误、引用消失 | 端到端稳定性不足；原因可能涉及随机性或平台条件 | 分开统计内容波动和服务失败；记录版本、网络与批次，无法控制的条件明确列出 |

这些实验能形成有价值的“缺陷地图”，不需要知道模型权重；其强度来自控制变量和证据，而不是给根因贴一个听起来技术性的标签。

## 5. 子系统的数据与执行边界

建议的数据关系为：`family → scenario variant → session → turn/event → criterion result → defect → controlled replay`，分别表示场景家族、变体、会话、轮次/事件、评分项、缺陷与受控回放。所有输出保留版本与来源标识，不将同一家族改写视为新的独立患者样本。

| 边界 | 被测对象可以看到 | 被测对象不能看到 |
| --- | --- | --- |
| 患者会话输入 | 本轮话语、此前合法可见历史、实际提供的工具结果 | 隐藏患者事实、评分答案、故障种子与预期缺陷 |
| 模拟患者 | 冻结事实、披露条件、已披露记录、预设表达策略 | 正确答案与得分规则；不得依模型表现改变事实 |
| 评测与诊断 | 冻结评分规则、完整合法记录、适用机会、经验证的内部追踪 | 不可伪造黑盒内部轨迹；不能把未来披露事实当作早期模型已经知道 |

黑盒导入应校验数据结构、轮次和角色、实验条件、来源与去标识状态。它只接受观测材料，不因为文件内出现某个“已确认工程故障”字段就信任这种判断。判断过程必须重新检查证据等级和观测边界。

自然语言语义判断与可确定的工程检查分开：状态字段是否更新、工具错误是否被记录、引用标识是否存在可以用程序检查；解释是否准确、建议是否适用、误解是否修复需要经校准的评分与人工复核。缺少人工临床评分时显示待评，不自动给临床通过。

## 6. 本次 v0.1 的交付口径

本次围绕四个合成场景家族建设第一条可运行闭环，每个家族有清晰版与压力版，共八个变体。四个家族是工程起点，不等于任务书的 24 个开发场景或 72 个研究家族，也不代表已经完整覆盖八模块。具体文件和运行命令以同目录使用说明及代码为准。

| 核心部分 | 本次原型用于证明什么 | 不能据此宣称什么 |
| --- | --- | --- |
| 数据合同与校验 | 用 JavaScript Object Notation（JSON，结构化数据交换格式）表达场景、运行、评分与对照；拒绝不合规开发输入 | 结构合法就是医学真值正确；自行标注“测试”即可进入正式准入 |
| 可见事件状态机 | 结构化的新增、未知、冲突和纠正事件可以保留来源并驱动更新；错误覆盖可用对照重现 | 已经解决患者口语的自动理解；人工结构化事件等同于模型自己识别 |
| 可解释检索 | Best Matching 25（BM25，基于词项相关性和长度归一化的检索排序）结合中文词项处理与适用性过滤，有明确排序和筛除原因 | 已完成语义向量检索、神经重排序或真实世界医学证据覆盖 |
| 多轮夹具与故障对照 | 固定前缀包含事先写好的用户与助手历史；执行器依据可见标注累积状态，只生成最后回答。故意丢弃纠正事件并从相同合法前缀修复回放，检查状态、实际输入与结果 | 夹具是医疗大模型；故意坏掉的基线与修复的差值等于对通用模型的提升 |
| 黑盒人工导入 | 小荷和通用模型会话能进入同一记录和评分框架 | 自动登录或采集了小荷；已经获得任何平台的真实测评结果 |
| 评分与诊断 | 适用项、未评项和测量无效有明确区别；内部证据不足时降级为假设 | 自动判断所有临床语义；从外部回答确认内部架构 |
| 家族配对报告 | 同条件可配对、未配对可见；以家族为单位给出差值与重采样区间 | 小规模合成家族足以得出人群泛化或商业模型排名 |

兼容 API 适配器可在明确配置后调用真实通用模型。当前 API 路径是将固定、合法的多轮前缀作为输入，生成最后一条回答；它不是动态患者模拟器，也没有自动完成自由问询。当前尚无真实专家评分、完整八模块临床评分、自由对话自动化或小荷自动采集。人工临床项没有标注时一律保留 `unassessed`（未评）。

本次没有实际调用付费模型或采集小荷真实结果。默认演示不需要密钥，不向外发送患者数据。命令行接口（Command-Line Interface，CLI）入口如下；导入及评测的具体文件结构见同目录使用说明与模板。

```bash
# 默认运行四个合成家族及其清晰/压力变体
python -m scripts.patient_eval demo --out /tmp/patient-eval-demo

# 导入人工记录的黑盒会话；输入与输出应放在受控本地目录
python -m scripts.patient_eval import --input /path/to/transcripts.json --out /path/to/imported.json

# 按同一场景合同评分；待人工审核的临床项不会自动通过
python -m scripts.patient_eval evaluate --suite medical/patient-eval/development/scenarios.json --sessions /path/to/imported.json --out /path/to/report

# 可选：显式配置后调用真实模型；供应商可能按调用计费
python -m scripts.patient_eval run-api --suite medical/patient-eval/development/scenarios.json --base-url https://example.com/v1 --model MODEL_ID --key-env MODEL_API_KEY --out /path/to/api-runs
```

导入输出为一个 JSON 数组文件；`run-api --out` 接收目录，并在其中写入 `sessions.json`、`results.json` 和 `report.html`。

示例 API 地址和模型名是占位符；密钥从环境变量读取，不能写入研究文件或提交仓库。真实运行只发送所选场景的合法可见输入，不发送隐藏真值、评分答案或故障标签。

本次持续集成只验证新子系统的代码和合成机制。持续集成（Continuous Integration，CI）通过、合成故障被检出、某次真实模型得分较高，三者均不自动改变现有阶段准入结论。

## 7. 评分、诊断和报告必须回答什么

### 7.1 每项指标保留分母

严重错误以会话为单位单列：一条会话发生多次同类错误可以生成多个证据，但不能伪装成多个独立患者样本。成功率要求适用的必要行为完成且没有严重错误；不能用礼貌或解释长度抵消严重错误。

澄清、必要信息问询、纠正吸收、证据支持、工具恢复、误解修复均以预先定义的“适用机会”为分母，同时保留截止轮次、证据和不适用理由。目标失败导致本应执行的必要步骤未发生，应计未完成；合法停止可以不适用；独立模拟器或采集器故障才是测量无效。

人工评分缺失时保留“未评”；不能在分母中悄悄去掉难例。报告至少同时给出计划数、有效数、无效数、未完成数、待评数、纳入比较的家族数及各项适用机会数。

解释评分分成五项，每项 0–2 分：通俗且准确、依据可理解、不确定性恰当、下一步可执行、错误复述得到修复。它不等于回答的词数，也不要求公开模型隐藏推理；评的是患者能看到的理由与解释。

### 7.2 从失败证据到修复任务

每张缺陷单包含：可见症状、影响与严重度、会话及关键轮次、期望行为依据、观测等级、候选原因、证据等级、反例、下一项区分实验、建议修复、回归集合。

有内部记录时，优先做可解释的单因素替换：修正可见状态、替换经过核验的相关证据、回放正确工具响应、补全此前确实合法的输入、改变生成或抽取策略。每次记录实际修改了什么；保持输入格式、长度和其他配置尽可能匹配，排除把多个有利变化捆绑成“算法有效”的情况。

故障注入成功与目标回答失败分开记录：工具被注入超时但系统合理恢复，属于恢复成功，不能为了提高检出率判失败。评分器灵敏度另用已确认有缺陷的受控输出验证。任务书 F01–F10 故障类全部覆盖属于后续完整验收；v0.1 不应根据少量已实现种子宣称十类能力完备。

### 7.3 报告形成两张独立成绩单

一张是被测平台表现：完整会话结果、八模块覆盖与分项、压力前后变化、失败案例、严重错误、未评项与证据等级。另一张是评测系统本身的质量：导入完整率、测量无效率、评分一致性、故障检出与误报、可复现性、耗时和运行成本。

统计比较按同一家族配对，先在家族内部汇总重复与变体，再做家族层面的自助重采样（bootstrap）区间。不能把每轮回答、每个评分项或同一家族十个改写当作独立样本。缺失配对单独列出，不能只留下候选系统成功的运行。首版四个合成家族的区间主要验证统计程序，不能支持人群推断。

## 8. 后续工作包：算法知识、工程任务与效果

| 工作包 | 对应算法与应学习知识 | 工程任务 | 目标效果与验收证据 |
| --- | --- | --- | --- |
| W01 数据与合同 | 分层抽样、按家族分区、近重复与污染检查、内容效度；先理解“独立样本” | 完善场景合同与溯源；真实问题去标识和审核；冻结版本与覆盖矩阵 | 四个合成家族扩为 24 个公开开发场景；研究版按任务书建立 72 个独立家族。相关变体不跨分区，原有已暴露案例不算新测试 |
| W02 患者模拟器 | 有限状态机、部分可观察任务、分支策略、条件生成、模拟器偏差 | 固定事实与触发披露；隔离评分材料；自然语言改写受约束；异常分支留痕 | 同问题不漂移患者事实，不补出不可得信息；人工验证自然度；变换表达策略后结论不过度依赖一个模拟器 |
| W03 多轮执行与状态 | 指代与否定识别、事件抽取、实体链接、时间推理、置信校准；状态逻辑与抽取误差分别测 | 将自然语言抽取结果接入有来源的状态机；记录实际模型输入；超时、重试、预算、取消与续跑 | 时间/人物纠正正确吸收，未知不被当作否定；输入遗漏可定位；目标失败保留结果。先通过抽取标注集再接全会话 |
| W04 证据和工具 | BM25、语义向量、混合检索、交叉编码器重排序、召回率与排序质量、来源与时效适用性 | 复用既有来源适配器；证据快照；工具参数合同；日期单位规范；可追踪的失败恢复 | 正确证据进入候选集并被有效使用；报告错误筛除和错误纳入；工具失败不被伪称成功。比较简单基线与单因素改进 |
| W05 评分与临床校准 | 评分量表、标注者一致性、偏差、置信区间；模型评分器的长度和位置偏差 | 冻结评分规则；盲评、复核、裁决；人机评分分歧审查；未评与无效状态 | 关键临床项有可信依据；严重错误不被平均分掩盖；评分可靠性有证据，而不是只报告模型评分器自己的信心 |
| W06 故障与因果诊断 | 对照实验、混杂因素、消融、反事实、可识别性、故障定位 | 完善 F01–F10；验证注入位置；匹配前缀回放；黑盒原因降级；保护故障标签不泄漏 | 能区分观测症状和内部根因；修复效果由配对回放支持；鲁棒恢复不误判成失败；评分器自身故障可被发现 |
| W07 报告与闭环 | 聚类分析、错误分布、家族配对统计、效应量和区间；谨慎使用小样本 | 统一运行与缺陷编号；版本比较；可追溯报告；任务分派和回归集合 | 每个主要缺陷能定位到证据与下一步修复；报告同时暴露算法、工程和测量系统不足；不以漂亮总分掩盖覆盖缺口 |
| W08 真实模型改进实验 | 根据根因选择提示策略、检索重排、监督微调（Supervised Fine-Tuning，SFT）或偏好优化；先学基线与消融 | 接入真实模型；冻结基线/候选/评分版本；记录成本与性能；独立测试由既有流程放行 | 至少一次单因素改动获得可复核改善，并报告未改善家族与回归风险。黑盒应用不能改权重时，任务是证明缺陷与区分假设，不能宣称修复其内部算法 |

当前工作包状态：W01、W03、W04、W05、W06、W07 为部分原型；W02 的动态模拟器和 W08 的真实模型改进实验仍待实施。可调用接口不等于完成真实模型比较；结构化事件状态机不等于完成自然语言抽取。

学习顺序建议：实验设计和评分口径 → 状态机与可观察日志 → 检索与适用性 → 故障注入与受控诊断 → 真实模型与标注 → 有证据需求时再做模型训练。先用一个小而完整的修复闭环证明能力，再扩大模型或算法复杂度。

排期应按可用开发者、临床审核者和采集能力制定。未确定人力时不承诺按若干周自动达到临床就绪。优先级是 M0 → M1 的一条完整证据链，而不是同时铺开六类业务和十种训练方法。

## 10. 与既有 GroundSignal 的后续连接点

1. **证据连接**：将新检索记录关联既有 `passage_id`、文档快照与适用信息；对缺少来源、版本或人群字段的数据保留未知状态，不静默补成可信。
2. **案例连接**：原有案例以开发来源映射进新 `family_id`；保留原始案例编号和已暴露状态，不能因新包装而变成独立测试。
3. **失败连接**：将新缺陷单的行为标签交给原有干预路由器，同时保留观测等级与证据等级；只有经过验证的内部对照才能提高根因确定性。
4. **回归连接**：输出明确的案例、会话、家族、版本、适用指标和严重错误后，再适配既有回归入口；不把待评临床项映射成通过。
5. **准入连接**：本次仅开发轨。正式独立评测与任何训练数据导出仍需原有流程授权；新增文件或 CI 成功不授予这些权限。
