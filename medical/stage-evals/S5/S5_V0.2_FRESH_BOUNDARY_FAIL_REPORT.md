# S5 v0.2 — Fresh Boundary First Observation: FAIL

## Decision

**Fresh structural gate: FAIL**

**S5 stage release: BLOCKED_GOLD_REVIEW**

**S6 automatic trust: BLOCKED**

Target implementation: `37a89d14b37a1e2b3b823e933b4a7bfbd3038af8` (frozen before creation of this suite).

This version intentionally contains **no implementation repair**. It records the first observation before any response to the failures.

## What passed

The new synthetic family passed referential integrity and materialized successfully:

```text
families                  1
cases                     5
dev                       3
regression                1
heldout                   1
decision contracts        5/5
provenance complete       5/5
training eligible           3
training blocked            2
```

Baseline partition behavior also passed: ordinary heldout/regression cases were blocked from training export, while dev remained exportable.

The model-facing prompt did not expose a gold sentinel. The release predicate also correctly preserved `0/1` gold approval and returned `BLOCKED_GOLD_REVIEW`.

## First-observation failures

### S5-F4 — PROVENANCE_AUTHORITY_NOT_VERIFIED

A materialized heldout case became exportable after changing only its local provenance from `heldout` to `dev` and setting `training_eligible=true`.

The exporter therefore treats mutable case-local provenance as authority rather than verifying it against a trusted suite/manifest contract.

### S5-F5 — UNPROVENANCED_OR_UNKNOWN_SPLIT_NOT_FAIL_CLOSED

Two generic bypasses succeeded:

1. remove `benchmark_provenance`, then provide top-level `split=dev`;
2. use an unknown provenance split `train` with `training_eligible=true`.

Both became exportable. Missing or non-allowlisted partition authority therefore does not fail closed.

### S5-F6 — MATERIALIZED_PAYLOAD_INTEGRITY_NOT_ENFORCED

A dev materialized case remained exportable after the prompt was mutated after materialization. A source-case SHA-256 existed, but no check bound the actual payload entering export to that digest or to an equivalent materialized-payload digest.

The current hash fields therefore establish lineage but not export-time payload integrity.

### S5-F7 — DECISION_EXEMPTION_SCHEMA_MATERIALIZER_DIVERGENCE

`materialize_s5_cases.py` accepts an exemption-only decision contract when `decision_contract_exemption` has a type and rationale. The JSON schema simultaneously requires root-level `graph_eval`.

The same case can therefore be valid at the materializer boundary and invalid at the schema boundary.

## Why this matters

The exposed v0.1.1 regression proved that the repaired happy-path boundary works on existing P0 assets. The fresh v0.2 result shows that the boundary is not yet authoritative under adversarial interface mutation.

This is a more consequential failure than a single wrong benchmark answer: it can alter which examples are eligible for post-training data and makes case validity depend on the entry point used.

## Correct disposition

Do **not** relabel this suite as fresh after repair. It is now exposed.

The next implementation version should, generically:

1. authenticate partition provenance against an immutable/authoritative suite-manifest contract at export;
2. require explicit allowlisted partition identity and remove permissive fallback for S5 benchmark-origin cases;
3. bind and verify the materialized payload digest before export;
4. unify schema and materializer decision-contract semantics.

After those repairs pass this suite as exposed regression, freeze the repaired implementation and construct a second genuinely new post-freeze S5 boundary suite.

This report makes no clinical-performance claim and does not represent expert review.
